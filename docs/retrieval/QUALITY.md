# Проверяемое качество retrieval

`packages/retrieval/evaluate.py` использует 10 **синтетических** POI и 27 запросов, с вручную заданными релевантными ID в `tests/fixtures/quality-cases.json`. Корпус не является выгрузкой Астаны. Все записи, источники и ID помечены synthetic. Judgments записаны отдельно от кода словаря и не вычисляются им. Нет случайности, внешних провайдеров или платных вызовов.

Проверка 19 октября 2026:

| Показатель | Результат |
|---|---:|
| Положительные запросы | 24 |
| Recall@3, среднее по положительным запросам | 0,9167 |
| MRR@3 по положительным запросам | 0,9167 |
| Правильно пустые результаты | 3 из 3 |
| Запросы с первым релевантным результатом на позиции 1 | 22 из 24 |

Покрыты coffee/кафе, музей/мұражай, библиотека/кітапхана, парки/серуен, галерея, площадка, ресторан, кино, сады, имена из source aliases, отрицание категории и пожелания зарядки/тишины. Два намеренно сохранённых промаха показывают границу словаря: **“Somewhere to study”** не находит библиотеку, **“Дәмді ас”** не находит ресторан. Это не доказательство готовности semantic search. Расширять словарь по этим же примерам и затем сообщать новое качество как независимое нельзя; нужен новый отложенный набор.

Unit-тесты дополнительно проверяют точный radius, порядок score→distance→ID, candidate_limit/pool, отсутствие подстановки случайных nearby, exact JSON equality, unknown/conflicting/dynamic required, отсутствие выдуманных matched_fact_keys, source aliases, отмену, timeout, immutability и port factory.

Корпус мал и удобен для регрессий. Метрики не оценивают живую Астану, полноту OSM, актуальность удобств, маршруты, пользовательское поведение или paid providers. Production выбор embedding/rerank модели по этому набору не обоснован.

## Интеграционный smoke с реальным snapshot

19 октября 2026 выполнены 7 запросов через настоящий `astana_city_data.create_repository` и этот Retriever на sample из 300 OSM POI. SHA-256 файла: `48a82bc4fc58fb3d699422de13a4cde1a79c951137425b5e8ad044f3cc52b064`. Это sample, а не полный охват Астаны.

«кофе» нашёл Q-cafe, Coffee Like и Coffee BOOM; «мұражай» — три museum; `library` — три library; «серуен» — три park; «Не кафе, а музей» — только museum. `quiet cafe with a power socket` вернул café-кандидатов с пустыми matched_fact_keys: сведений о тишине/розетках нет, они не объявлены подтверждёнными. `quantum teleportation` вернул пустой результат. В том запуске retrieval занимал 463–513 мс на запрос; это одиночный локальный smoke, не latency benchmark.

Воспроизведение после установки обоих пакетов в workspace:

```powershell
$env:ASTANA_POI_PATH = (Resolve-Path 'data/samples/astana-osm.json').Path
.venv/Scripts/python.exe packages/retrieval/smoke_snapshot.py
```

Script не импортирует данные из сети и не вызывает AI; он использует публичные порты. Он проверяет категории и отсутствие synthetic markers. Это подтверждение совместимости и basic search, не независимая оценка релевантности, полноты, работы заведений или удобств.

## Следующий реальный набор

После импорта нужно сохранить snapshot hash/import timestamp и отдельно разметить 30–50 запросов жителей на RU/KK/EN: район и origin, категория, редкие имена, смешанные языки, отрицания, required/unknown, намеренно пустые результаты. Разметку делать по данным источников, а удобства с неизвестной истинностью отмечать неизвестными. Recall измерять как минимум относительно полного разрешённого snapshot, чтобы nearest-pool truncation не пряталась в знаменателе. Origin/сырой текст реальных пользовательских запросов не собирать без отдельного согласованного процесса.

Для повторяемого сравнения фиксировать snapshot, lexicon_version, configuration, pool_limit, k, модель/dimensions/index_version (когда появятся), runtime и judgments. Отдельно показывать качество RU/KK/EN, no-match precision, известные нарушения required (должны быть нулём), p50/p95 времени и число fallback. Результаты live smoke с реальными категориями подтверждают интеграцию, но не заменяют независимую разметку релевантности.
