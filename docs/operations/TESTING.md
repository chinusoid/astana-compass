# Как потестить Astana Compass

На Windows сначала используйте [WINDOWS.md](WINDOWS.md): ниже команды bash.
Для реального каталога есть отдельные проверки, описанные в конце этого файла.

Теперь можно проверить пользовательский интерфейс в `apps/web`, backend через `/sandbox`, Swagger `/docs` и готовый HTTP smoke-тест. В режиме `fixture` используются **три явно синтетических места**, из них два с подтверждённым `indoor=true`. Они не представляют реальные заведения Астаны. Без настроенного провайдера объяснения формируются детерминированно; вызовов языковой модели нет.

После запуска API ниже откройте второй терминал, перейдите в `apps/web` и выполните `pnpm install --frozen-lockfile`, затем `ASTANA_ALLOW_FIXTURES=true pnpm dev`. Нужны Node.js 24.19.0 и pnpm 11.25.0. Интерфейс доступен на `http://127.0.0.1:3000`; для API на другом порту добавьте `ASTANA_API_URL=http://127.0.0.1:18080` к команде frontend. Проверьте рекомендации от точки `51.090, 71.420`, выбор двух остановок и общий маршрут с возвратом. Переключите RU / KK / EN; обязательная доступность для коляски должна дать отсутствие подходящих результатов. [Подробности интерфейса](../../apps/web/README.md).

`/sandbox` остаётся техническим экраном проверки backend. Шаги ниже относятся к API и работают независимо от frontend.

## 1. Открыть правильную папку

Команды выполняются из корня существующего клона — рядом должны лежать `pyproject.toml`, `uv.lock`, `scripts/` и `services/`.

Откройте терминал в каталоге клона или распакованного проекта. Если терминал уже открыт в корне репозитория, повторный `cd` не нужен. Для запуска backend нужен `uv` на PATH; Node.js и Docker для этого сценария не требуются.

## 2. Запустить API в первом терминале

```sh
uv sync --locked --all-packages
ASTANA_MODE=fixture LLM_PROVIDER=none bash scripts/dev.sh
```

Сервер по умолчанию слушает `127.0.0.1:8000`. Оставьте этот терминал открытым.

Если порт 8000 занят, используйте другой порт, например:

```sh
ASTANA_MODE=fixture LLM_PROVIDER=none bash scripts/dev.sh --port 18080
```

Тогда во всех адресах ниже замените `8000` на `18080`. Не останавливайте чужой сервис ради освобождения порта.

Переменные задаются только для запускаемой команды. Файл `.env` автоматически не загружается. Ключи провайдеров, если они понадобятся позже, передаются серверу через окружение; их не нужно вводить в `/sandbox`, Swagger или frontend. Настройки live-адаптеров и опциональной модели описаны в [LOCAL.md](LOCAL.md).

## 3. Проверить в браузере

Откройте:

- [Sandbox](http://127.0.0.1:8000/sandbox) — отправка тестовых запросов и просмотр ответов.
- [Swagger](http://127.0.0.1:8000/docs) — все HTTP endpoints и схемы.
- [Readiness](http://127.0.0.1:8000/v1/health/ready) — ожидается `status: "ok"`.
- [Каталог](http://127.0.0.1:8000/v1/places) — ожидаются три synthetic-места.

В sandbox пройдите сценарии ниже. Если нужный параметр не выведен отдельной кнопкой или полем, отправьте соответствующий запрос через `/docs`: раскройте endpoint → **Try it out** → измените JSON → **Execute**.

| Что проверить | Действие | Ожидаемое поведение |
|---|---|---|
| Каталог | Загрузить места | Три места с `is_synthetic=true` и ID с префиксом `synthetic:` |
| Помещение | `POST /v1/recommendations`: `indoor=true`, `strength="required"`, пешком, достаточно времени | Есть подходящие варианты; каждый подтверждён известным indoor-фактом и помещается в бюджет |
| Неизвестный обязательный факт | Заменить ограничение на `wheelchair_accessible=true`, `strength="required"` | `status="no_match"`, пустые `places` и `recommendations`, объяснение ограничения |
| Неподдерживаемый транспорт | Установить `transport="cycling"` | HTTP 422, `error.code="unsupported_transport"`; скрытой замены на walking нет |
| Неверные координаты | Установить `origin.lat=91` | HTTP 422, `error.code="invalid_request"` |
| Выбранный маршрут | `POST /v1/itineraries`: выбрать два indoor-места в явном порядке, передать их в `place_ids`, включить `return_to_origin=true` | Порядок и выбранные ID сохранены; возврат учтён; дорога плюс оба посещения укладываются в `available_seconds` |

Для ручной проверки через Swagger можно получить готовый synthetic-запрос с текущим временем UTC+05:

```sh
uv run --locked python -c 'import json; from scripts.smoke import request_template; print(json.dumps(request_template(), ensure_ascii=False, indent=2))'
```

Скопируйте JSON в `POST /v1/recommendations`. Для itinerary добавьте `place_ids` из каталога. В тестовом запросе `available_seconds=7200`, `limit=3`, `return_to_origin=true`. Числа длительности — секунды, расстояния — метры. У fixture-маршрутов ожидается `method="approximate"`, `geometry=null` и явные допущения; они не являются построенным маршрутом по улицам.

## 4. Автоматически пройти весь smoke во втором терминале

Из того же корня репозитория:

```sh
uv run --locked python scripts/smoke.py --base-url http://127.0.0.1:8000
```

Если сервер запущен на альтернативном порту:

```sh
uv run --locked python scripts/smoke.py --base-url http://127.0.0.1:18080
```

Ожидается восемь строк `PASS` и финальное `PASS smoke (8/8 checks; synthetic fixtures only)`. Проверяются оба health-endpoint, каталог, indoor-рекомендации, неизвестный required-факт, два ошибочных запроса и itinerary с выбранными местами. Код завершения: `0` при успехе, `1` при ошибке проверки. Smoke останавливается на первой ошибке; он не записывает feedback и не проверяет его хранение.

CLI использует только стандартную библиотеку и работает также без установленного workspace:

```sh
python scripts/smoke.py --base-url http://127.0.0.1:8000
```

Если `astana_contracts` установлен, дополнительно включается проверка канонических схем и invariants. Рекомендуемый запуск через `uv run` обеспечивает эту проверку. Без пакета остаются независимые HTTP и поведенческие проверки; об этом сообщается строкой `INFO`.

Самопроверка HTTP-клиента не требует запущенного API:

```sh
python scripts/smoke.py --self-test
```

Она проверяет ожидаемые/неожиданные статусы, некорректный JSON, отказ при live-режиме, безопасную обработку ошибки соединения и код завершения. Временный HTTP-сервер закрывается в конце проверки.

## Если появилась ошибка

- `HTTP connection failed or timed out`: проверьте адрес, порт и терминал сервера. При необходимости задайте `--timeout 30`.
- Readiness 503: процесс работает, но необходимые сервисы не готовы. Для текущего тестового набора явно запускайте `ASTANA_MODE=fixture LLM_PROVIDER=none`.
- `Fixture mode required`: выбран live-сервер или другой сервис. Smoke рассчитан на fixture-режим и не считает реальные данные тестовыми.
- Ошибка sync/lock: проверьте, что запускаетесь из актуального клона и не меняли dependency manifests отдельно от `uv.lock`.

Для остановки собственного API нажмите `Ctrl+C` в терминале запуска. Успешный smoke подтверждает этот интеграционный сценарий на synthetic-данных; качество реальной городской базы, внешних маршрутов и ответов модели проверяется отдельно после подключения соответствующих модулей.

## Реальный каталог без внешних провайдеров

После locked install из корня:

```sh
uv run --locked pytest tests/integration/test_real_snapshot.py
```

На Windows при ограничениях системного TEMP добавьте
`--basetemp .pytest_cache/real-snapshot-tmp`. Тесты загружают собранный
`data/samples/astana-osm.json` через реальные factories в live-режиме.
Проверяются источник/атрибуция и 300 POI, рекомендации RU/KK/EN, выбранный
план с возвратом, отказ по неизвестному required, unrelated no-match и
readiness 503 при отсутствующем снимке. Внешний HTTP запрещён тестовым guard;
ключи не нужны. Приблизительный путь остаётся без выдуманной геометрии.

`packages/retrieval/smoke_snapshot.py` отдельно проверяет семь поисковых
сценариев; команды и границы оценки — в [QUALITY.md](../retrieval/QUALITY.md).
CI также запускает `infra/check_image.py` по установленным runtime wheels в
контейнере с отключённой сетью и явно смонтированным снимком. Это проверки
реальных POI, но не hosted AI, уличной маршрутизации, качества всех удобств
или live-работы картографических тайлов.
