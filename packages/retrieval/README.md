# Astana retrieval

Рабочий локальный `Retriever` для нормализованного snapshot: категории и небольшой словарь RU/KK/EN, взвешенный BM25 и детерминированный выбор кандидатов. Используется публичный `PlaceRepository`; файл данных и импорт принадлежат `astana_city_data`. Сетевых запросов, ключей, LLM, embeddings или отдельной vector DB в этом пакете нет.

```python
from astana_retrieval import create_retriever

retriever = create_retriever(repository=repository, config={"mode": "live", "timezone": "Asia/Almaty"})
result = await retriever.retrieve({
    "query": "Тихое кафе с розеткой", "locale": "ru",
    "origin": {"lat": 51.1, "lon": 71.4}, "radius_meters": 5000,
    "candidate_limit": 12, "constraints": [],
})
await retriever.aclose()
```

Вход и выход проходят канонические `RetrievalRequest`/`RetrievalResponse`. Factory не выполняет I/O. Repository заимствован: `aclose` retriever не закрывает его. В API он закрывается владельцем composition.

## Ранжирование и границы

1. Один вызов `repository.nearby` получает максимум `ASTANA_RETRIEVAL_POOL_LIMIT` ближайших POI (по умолчанию 1000, допустимо 100–1000). Полная выборка этого размера сопровождается предупреждением о возможном пропуске релевантных мест дальше по расстоянию. На один вызов установлен timeout.
2. Повторно проверяются `Place`, уникальность IDs и сферический радиус по haversine с радиусом Земли 6 371 008,8 м. Это географический фильтр; он не является пешим маршрутом. Попадание в radius не заменяет построение маршрута.
3. Подтверждённое нарушение static required исключает место. Сравнение — точное JSON-равенство: `true` отличается от `1`, включая массивы. Unknown/conflicting required и `open_at_requested_time`/`weather_suitable` сохраняются для последующих проверок при наличии поисковой релевантности; динамическое значение из snapshot никогда не считается текущим.
4. Небольшой версионированный словарь распознаёт категории, распространённые формы слов и удобства на RU/KK/EN. Это ручные поисковые расширения, не обученная multilingual модель. Отрицательные категории исключаются; отрицательные/необязательные удобства не становятся положительными сигналами. Отрицание ограничено локальной фразой: «без сахара кофе» не исключает кафе. Walk/серуен предлагает прогулочные категории только без явной категории назначения. Набережная и архитектура требуют соответствующих слов в исходном названии или описании; категория park или attraction сама по себе не доказывает эту тему. В «coffee near a museum» музей — текстовый ориентир, а кафе — цель. Ориентир не геокодируется: warning сообщает, что используется выбранная точка карты и близость к ориентиру не проверена. Поддержаны частые формы «кафеге/кафеде», но сложная грамматика, произвольные опечатки и все формы казахского языка не покрыты.
5. До интерпретации категорий ищутся буквальные исходные названия и allowlisted OSM/Wikidata aliases. Совпадение названия получает +100, но не отменяет radius, required или отрицание категории/имени. Поэтому The Garden не теряется как ресторан, а Coffee Bus не становится кафе. Остаточные слова просьбы и удобства не расширяют буквальную цель до других садов; явно запрошенная вторая категория или кухня может добавить кандидатов. Индексируются исходные name, description, категории и известные факты. `name:ru`, `name:kk`, `name:en` используются лишь при наличии known факта из источника. Переводы не создаются. Для обычных слов имена имеют вес 3, описание — 1, known true удобства — 2. Совпадение структурной категории даёт единичный балл без штрафа за длину описания. Вхождения нормализованы до присутствия терма в каждом поле, чтобы повторение рекламного текста не усиливало результат неограниченно. BM25 использует `k1=1.2, b=0.75`; IDF вычисляется по ограниченному корпусу после фильтров.
6. Текстовая релевантность первична. Только при равном score учитываются подтверждённые preferred условия, наличие описания для запроса только по категориям, расстояние и ID. Число совпавших фактов не добавляет баллы поверх текстового score. При отсутствии текстового сигнала и подтверждённых явно заданных условий возвращается пустой результат. Случайное ближайшее место не подставляется. Вход с неизвестным названием не считается подходящим только за счёт побочного условия вроде `indoor`.

Для общих и смешанных прогулок кандидаты с сопоставимой релевантностью (не ниже 75% лучшего оставшегося score) чередуются по темам: зелёные зоны, набережная, архитектура, искусство. Близкие объекты с одинаковым названием по возможности уступают место отличающемуся варианту. Названная пользователем цель не расширяется ради разнообразия; узкий запрос «кофе» не превращается в прогулку по паркам. Это детерминированный подбор, не оценка красоты, доступности или безопасности. При запросе у реки используется текст источника, а не вычисление расстояния до воды. Если подтверждено только два подходящих места, третье не выдумывается.

`matched_fact_keys` включает только реально присутствующие known факты, совпавшие с запросом или explicit constraint. Слова «тихо» в описании могут влиять на текстовый score, но не создают `quiet` fact/evidence. Извлечённые из текста пожелания не превращаются в hard filters; окончательные required проверки выполняет recommender после context enrichment.

Каждый hit имеет `score_kind="lexical"`; `strategy="snapshot-bm25-ru-kk-en-5"`. Пользовательский warning на языке запроса объясняет поиск по названиям, категориям и словам описания, а также необходимость уточнять сложные пожелания. Embeddings не подключены. Score — относительный сигнал, не вероятность и не сравнимая между разными запросами оценка качества.

## Настройка

| Серверная переменная | По умолчанию | Допустимо |
|---|---:|---|
| `ASTANA_RETRIEVAL_POOL_LIMIT` | 1000 | целое 100–1000 |
| `ASTANA_RETRIEVAL_TIMEOUT_SECONDS` | 5 | конечное число больше 0 и не больше 30 |

Запрос ограничен 2000 символами, 20 constraints и canonical candidate_limit 1–100. Индексируются не более 500 символов каждого имени и 8000 символов описания. Неправильная конфигурация, сломанные repository payloads и превышенный pool отклоняются; исключения не включают сырой запрос. Cancellation сохраняется. Пользовательские координаты, запросы и результаты не записываются в логи/кэш. Нет скрытого сетевого fallback или платного вызова.

## Проверки

До регистрации workspace координатором можно запускать из корня PowerShell:

```powershell
$env:PYTHONPATH = (Join-Path (Get-Location) 'packages/retrieval/src')
.venv/Scripts/python.exe -m pytest packages/retrieval/tests
.venv/Scripts/python.exe -m ruff check packages/retrieval
.venv/Scripts/python.exe packages/retrieval/evaluate.py
```

Последняя команда явно работает с отдельным синтетическим корпусом и ручными judgments. Она не измеряет качество реальных заведений. Подробнее: [качество и ограничения](../../docs/retrieval/QUALITY.md), [PostgreSQL/pgvector roadmap](../../docs/retrieval/POSTGRES-ROADMAP.md).

## Названия, опечатки и реальные данные

OSM name/alt_name/short_name/official_name/int_name и Wikidata label/aliases
индексируются только при наличии known source fact. Имена читаются буквально,
без выполнения текста источника. Максимум 64 варианта на место, до 500 символов.
Односимвольная опечатка рассматривается только для токенов длиной ≥5, одного
алфавита и единственного подходящего source token; пользователь видит warning.
Это не универсальное исправление казахской грамматики или транслитерации.

Пицца, частые формы `пицу`/`пицы`/`пиццу`, казахские формы и `pizza` задают
отдельное поисковое намерение кухни. Оно требует known `osm:cuisine` с evidence:
точного тега `pizza` или `italian_pizza` среди строковых значений через `;`/`,`
либо в списке у cafe или restaurant. Имя заведения, описание и общий тег `italian` не подтверждают пиццу.
Совпадение отмечается реальным ключом `osm:cuisine`; новая категория Place не
создаётся. Отрицание пиццы исключает только подтверждённые совпадения кухни.
Смешанный запрос сада и пиццы может вернуть оба типа кандидатов; порядок
посещения и соединённые маршруты определяет recommender.
`Пиццерия`/`пиццерию`/`пиццерии`/`пиццерией` и `pizzeria` используют то же
подтверждение кухни. `Перекусить`/`пообедать`/`поужинать` используют существующее
намерение restaurant, не приписывая заведению определённое блюдо.

Для исходных имён `Ботанический сад` и `Ботаникалық бақ` поддержаны ограниченные
падежные формы, включая `ботаническом саду` и `Ботаникалық баққа`. Это сопоставление
известных имён, а не перевод любого сада. На snapshot из 628 мест RU/KK/EN aliases
указывают на один `osm:way/1196402246` с категорией park. Отрицание такого имени
исключает сам объект, даже если его категория отличается от слова «сад».

Имена ориентиров после near/у/возле и перед казахскими жанындағы/маңындағы
маскируются при определении цели. Местоположение ориентира не вычисляется;
близость к нему не обещается. «study»/«позаниматься»/«оқуға», «Дәмді ас» и
«paintings» дают ограниченные категории только без более явной цели. Короткое
имя «Дәмді» не перехватывает полную фразу «Дәмді ас».

`evaluate_real.py --snapshot data/samples/astana-osm.json` проверяет 45 авторских
регрессионных запросов на pinned snapshot из 628 мест. SHA файла и source-based
judgments сохранены отдельно; смена snapshot требует проверки judgments.
Это не независимая оценка продуктового качества. Сравнение старой и новой
реализации на одинаковых данных: [QUALITY.md](../../docs/retrieval/QUALITY.md).


Семантические этапы могут передать `categories`, `named_place` и `cuisine` через канонический RetrievalRequest. Категории проверяются по категориям источника (OR), полное имя — по нормализованному исходному имени/alias, кухня — по known `osm:cuisine` с существующими evidence. Совпадение части чужого имени или случайного слова в описании не заменяет эти фильтры. Нормализованный тип кухни может быть любым структурированным тегом источника; общая японская/итальянская кухня не подтверждает суши/пиццу. Неподтверждённый тип или блюдо дают пустой результат для этого этапа.
